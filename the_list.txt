# 🔴 P0 — Fix these before tuning anything

## 1. The wheels are literally inside the chassis

Current dimensions:

```c
CHASSIS_HALF_Y = 0.075
WHEEL_RADIUS   = 0.05
WHEEL_Y_OFFSET = -0.075 - 0.05 + 0.01
               = -0.115
```

At rest:

```text
chassis center Y = 0.165
chassis bottom   = 0.165 - 0.075 = 0.090

wheel center     = 0.165 - 0.115 = 0.050
wheel top        = 0.050 + 0.050 = 0.100
```

So:

```text
             chassis
        ┌───────────────┐
 y=.100 ├────wheel──────┤  ← wheel top
        │               │
 y=.090 ├───────────────┤  ← chassis bottom
        │               │
 y=.050 │ wheel center  │
```

**There is 10 mm of geometric penetration.**

And the wheels are also:

```text
x = ±0.24
chassis edge = ±0.225
```

with a wheel half-width of 0.02, so the wheel extends 5 mm into the chassis in X as well.

The robot therefore begins life with four cylinders overlapping their parent chassis.

And I found **no collision filtering whatsoever for jointed bodies**.

The physics world explicitly does:

```c
collision_cylinder_cube(wheel, chassis, ...)
```

and then separately:

```c
constraint_solve_all(...)
```

So the solver is simultaneously being told:

> "Wheel must remain attached to this point."

and

> "Wheel must be pushed out of the chassis."

That's exactly the kind of hidden force loop that produces:

* vertical jitter
* wheel chatter
* weird chassis pitch/roll
* excessive solver work
* traction changing depending on solver iterations
* strange behavior when turning
* unexplained energy injection

### Fix

Either:

**A. Give the wheel actual clearance**

For example, make the wheel center at least:

```text
chassis_bottom - wheel_radius
```

so:

```c
WHEEL_Y_OFFSET <= -0.125f
```

with a little extra clearance, perhaps `-0.1275f` or similar.

**OR**, preferably:

**B. Add collision filtering between the chassis and its four wheel bodies.**

That is the physically correct solution for a constrained wheel assembly.

I would do **both**: correct the geometry and explicitly prevent self-collision between the robot's connected bodies.

# 🔴 2. MFS's "driveline inertia" double-counts the chassis

This is probably the second-biggest physics problem.

MFS calculates:

```c
wheel inertia
+ rotor inertia * G²
+ chassis mass / 4 * r²
```

For the default 30:1 motor:

```text
wheel inertia:
0.5 × 0.2 × 0.05²
= 0.00025 kg·m²

reflected rotor:
2e-7 × 30²
= 0.00018 kg·m²

reflected chassis:
2.2 × 0.05²
= 0.00550 kg·m²

total:
≈ 0.00593 kg·m²
```

The physical wheel itself is only:

```text
0.00025 kg·m²
```

So MFS makes the wheel body about:

**23.7× more rotationally inertial than its actual wheel inertia.**

But here's the subtle part:

### The `m × r²` load is already represented by the chassis rigidbody.

The solver already has:

```text
wheel
    ↓ contact impulse
ground
    ↓
chassis mass = 8 kg
```

The chassis has its own translational inertia.

So when MFS additionally writes:

```c
wb->inertia_tensor_local.matrix[0][0] = i_axle_eff;
```

it has effectively added the chassis's translational inertia to the wheel **while retaining the chassis's original mass**.

That's double counting.

For four equal wheels under pure forward motion, the correct generalized inertia is approximately:

```text
4 × (wheel inertia + reflected rotor inertia)
+ chassis_mass × r²
```

MFS instead gives the wheel bodies the reflected chassis load **and then still has the chassis mass present**.

For the default 30:1 robot, the total effective forward inertia becomes roughly **1.93× too large**.

So you're effectively making the robot almost twice as inertial as intended.

### This is why I don't want this "fixed" by changing the 0.0055 number.

The concept is wrong.

The proper solution is:

```text
physical wheel body:
    real wheel inertia

motor:
    reflected rotor inertia

physics constraints/contact:
    naturally provide chassis load
```

Don't bake chassis translational inertia into the wheel's rigidbody inertia.

# 🔴 4. Even if wheel-lock were alive, it violates momentum conservation

This code runs **after** the entire contact/constraint solver:

```c
rb->angular_velocity =
    rb->angular_velocity + axle * delta_omega;
```

That's a direct velocity edit.

There is no equal-and-opposite impulse applied to:

* the chassis
* the ground
* the revolute joint

So the wheel can simply lose angular momentum after the solver has finished.

Imagine:

```text
robot moving
wheel spinning
↓
solver finishes
↓
MFS wheel lock edits wheel ω
↓
wheel suddenly stops spinning
↓
chassis still has its old velocity
```

Next frame the contact solver has to clean up the inconsistency.

That's an artificial source/sink of momentum.

If wheel braking is desired, it belongs as a **torque/impulse inside the dynamics**, not as a post-solver velocity mutation.

# 🔴 8. The motor efficiency is mathematically cancelled out

This is subtle but definite.

You calculate:

```c
kt = stall_torque /
     (stall_current * gear_ratio * efficiency);
```

then:

```c
torque = kt * current * efficiency;
```

and:

```c
output_torque = torque * gear_ratio;
```

The efficiency therefore cancels.

At stall:

```text
(stall_torque / (I × G × η))
× I × η × G

= stall_torque
```

So:

```c
efficiency = 0.85
```

and:

```c
efficiency = 0.80
```

do not actually reduce mechanical output torque.

The code's comment claims MFS_318 is reconciling the energy discrepancy with additional losses.

**It doesn't.**

There is no actual `τ_friction` term in `motor_update()`.

So the model has:

```text
electrical power
≠
mechanical power
+ copper loss
+ modelled mechanical loss
```

by a large amount.

For example, at the default 30:1 motor's midpoint, the model can have roughly:

```text
electrical power ≈ 109 W
copper loss     ≈ 54 W
mechanical      ≈ 15 W
```

leaving about **40 W unexplained**.

That isn't necessarily catastrophic for driving, but it means the motor/battery/thermal model cannot be considered energetically accurate.

# 🟠 14. The MFS robot is using ground-truth odometry

This is one of the most misleading pieces of the current system.

You track wheel radians:

```c
robot->wheel_radians += omega * dt;
```

but then your actual pose estimate is:

```c
odom_x += chassis_vel.x * dt;
odom_z += chassis_vel.z * dt;
odom_theta += yaw_rate * dt;
```

That's not wheel odometry.

That's:

> **perfect simulator ground-truth velocity integration.**

A real robot does not know `chassis_vel`.

This makes the simulator look much more accurate than a real robot whenever there is:

* wheel slip
* mecanum scrub
* collision
* wheel lift
* battery sag
* inaccurate wheel radius
* roller slip

So any autonomous algorithm tested against this odometry will get a falsely optimistic result.

And there's another bug:

### You integrate the velocity before physics has produced the new velocity.

`drivetrain_update()` happens:

```text
motor
↓
odometry
↓
physics_world_step()
```

So odometry uses the **pre-step chassis velocity**.

That's a one-tick temporal lag.

# 🟠 15. The wheel/chassis self-collision is made worse by the cylinder-cube approximation

Even after fixing the 10 mm geometry overlap, MFS's cylinder-vs-cube collision is an approximation:

```text
5 samples along cylinder axis
+
sphere-vs-OBB style contact
```

The code itself acknowledges:

```text
contacts between samples can be missed
```

This is particularly problematic for wheels against:

* field walls
* chassis geometry
* obstacles

because the cylinder has flat endcaps but the approximation effectively treats sampled centerline points as spheres.

And the contact point is:

```c
cp->position = best_on_obb;
```

rather than a properly resolved midpoint/surface contact.

That gives the solver a potentially incorrect lever arm for torque.

For a wheel hitting a wall, that can produce wrong yaw/roll impulses.

# 🟠 16. MFS's anisotropic friction is not actually a proper friction cone

You have two independent friction constraints:

```text
grip axis
free/roller axis
```

and each independently gets:

```text
|impulse| <= μN
```

That means the combined friction vector can exceed the ordinary Coulomb limit.

Mathematically the allowed region is effectively a rectangle:

```text
       free
        ↑
        │ ┌─────────┐
        │ │         │
        │ │         │
        └─┼─────────→ grip
```

rather than a friction ellipse/cone.

With:

```c
μgrip = 0.8
μfree = 0.03
```

the numerical error is small.

But if you ever tune:

```c
roller_friction_coeff
```

upward, this becomes increasingly wrong.

A proper anisotropic friction model should use an ellipse or equivalent combined constraint.

# 🟠 17. The free-axis warm start is broken

MFS stores:

```c
accumulated_free_tangent_impulse
```

but when warm-starting the contact it initially applies:

```c
normal impulse
+
grip tangent impulse
```

The free-axis impulse isn't included in the initial warm-start velocity correction.

So the cache can remember:

```text
free tangent impulse = X
```

without actually having applied that impulse to the bodies.

Then the next iteration treats that value as accumulated history.

That's internally inconsistent.

And because the world-specific cache isn't actually being read anyway, this is mostly latent — but it's still broken.

# 🔴 18. Worse: the robot's contact cache is contaminated by the MPE world

This one is **very nasty**.

The legacy MPE physics loop ends with:

```c
contact_cache_save(NULL, active_manifold, manifold_count);
```

which writes to the **global** cache.

Then the MFS robot world runs.

`collision_prepare_solver()` reads:

```c
contact_impulse_cache
```

the global cache.

But the robot world does:

```c
contact_cache_save(world, ...)
```

which saves into:

```c
world->world_contact_cache
```

not the global cache.

So the actual flow is:

```text
MPE world
    ↓
global contact cache

MFS robot world
    ↓
reads global MPE cache
    ↓
solves robot

MFS robot world
    ↓
writes its own cache
    ↓
which it doesn't read next time
```

So the robot's warm start isn't actually persistent.

Worse, the MPE cache can contain object IDs that overlap with the robot world's object IDs.

Both worlds begin numbering bodies from 1.

That means the robot can potentially find a cache entry that belongs to an entirely different object in the legacy world if the IDs and property stamps line up.

**This is exactly the kind of thing that causes intermittent contact jitter that looks like "physics instability."**

The solution is simple architecturally:

> `collision_prepare_solver()` needs the world cache passed into it, rather than consulting a process-global cache.

# 🟠 20. The revolute axis correction violates angular momentum

MFS changed the axis-drift correction to:

```c
/* only correct wheel */
body_b->angular_velocity += ...
```

instead of correcting both bodies.

I understand **why** you did it: correcting the 8 kg chassis to fix a 0.2 kg wheel causes ugly chassis wobble.

But physically:

```text
constraint correction torque on wheel
```

requires an equal/opposite response somewhere.

MFS simply moves the wheel's angular velocity.

So this is numerically stable at the cost of physical correctness.

For a perfectly flat robot, it may be harmless.

For:

* wheel lift
* collisions
* ramps
* wall impacts
* tilted chassis

it can inject/remove angular momentum.

I'd replace this with a proper constraint impulse using the relative orientation error and both inverse inertias, rather than hard-pinning the chassis and teleporting angular velocity.

([goBILDA][7])

That's a 16.7% capacity difference.

But the more serious problem is the discharge model:

```c
avg_current = total_current * 0.25
```

This is basically a hand-tuned "make the battery last longer" coefficient.

It is not a battery model.

# 🟡 32. Empty battery still gives you 9 V

This:

```c

    terminal = 9.0f;
```

means:

```text
battery = 0%
motor = still gets 9V
```

That's not a battery reaching empty.

It's a hard-coded minimum motor voltage.

This can hide battery failures during autonomous testing.

---

# 🟡 33. Battery sag uses stale motor currents

The order is:

```text
read previous motor currents
↓
calculate battery voltage
↓
drain battery
↓
update motors
```

So the battery voltage for tick N is based on motor current from tick N−1.

At 60 Hz this isn't catastrophic, but under rapid direction/command changes it introduces a one-tick electrical lag.

---

# 🟡 34. MFS has no current controller / voltage-controller model

The motor gets:

```c

```

directly.

There is no model of:

* motor controller current limit
* PWM switching
* voltage droop under controller current limit
* controller update rate
* deadband
* braking mode

So the motor is essentially an ideal voltage source controlled by a scalar.

That's okay for a first-order model.

It's not enough for serious FTC electrical characterization.

# 🟠 35. `ftc_robot_set_wheel_commands()` can leave stale motors

That can create extremely confusing partial-drive bugs.

# ☠️ THE CENTRAL MONSTER

The current system has:

```text
GTK events
      ↓
input_write
      ↓
swap
      ↓
input_read
      ↓
copy
      ↓
main_inputs
      ↓
camera / dispatch / physics
```

The intent is presumably:

> Events happen asynchronously → collect them in one buffer → swap at frame boundary → consume a stable snapshot.

**But the implementation doesn't preserve state across buffers.**

You have:

```c
static input_status input_front;
static input_status input_back;

static input_status *input_write = &input_back;
static input_status *input_read  = &input_front;
```

and:

```c
void input_swap_buffers(void) {
    input_status *tmp = input_write;
    input_write = input_read;
    input_read = tmp;
}
```

The fatal assumption is that after swapping, the buffer becoming the writer automatically contains the current state.

It doesn't.

It contains **whatever state it had the last time it was read**.

---

# ☠️ Held keys become a square wave

Suppose:

```text
front.W = false
back.W  = false
```

Press W:

```text
back.W = true
```

Frame 1:

```text
swap

read  = back → W=true
write = front
```

`main_inputs.W` becomes true.

Frame 2:

```text
swap

read  = front → W=false
write = back
```

`main_inputs.W` becomes false.

Frame 3:

```text
swap

read = back → W=true
```

Frame 4:

```text
read = front → W=false
```

Therefore:

# **W = TRUE, FALSE, TRUE, FALSE, TRUE, FALSE...**

Same for:

* W
* A
* S
* D
* I
* J
* K
* L
* Space
* Shift
* essentially every persistent input

This is not a timing edge case.

**It is deterministic.**

So your description:

> "the ijkl motions don't hold up"

is exactly what the source predicts.

---

# ☠️ And this is why keys activate after you've released them

Now release W.

The release event only modifies whichever buffer happens to be `input_write`.

The other buffer may still contain:

```text
W = true
```

So the old state can come back on the next swap.

You therefore get:

```text
press
  ↓
true

release
  ↓
false

old buffer comes around
  ↓
TRUE AGAIN
```

Hence:

> "WASD or IJKL triggers movements even when I am not really pressing anything"

This isn't keyboard ghosting.

It's **software resurrecting stale input state.**

# ☠️ One-shot buttons are also broken

This is even worse because the same architecture is being used for things that are supposed to be one-shot events.

Take:

```c

```

The simulation does:

```c

```

But that's only changing the **copy**:

```text

     ↓

```

It does **not** clear:

```text

```

So the original event can return when that buffer rotates back into the read position.

Result:

```text

    menu_1 = true
    action executes

frame N+1:
    other buffer
    false

frame N+2:
    original buffer
    TRUE AGAIN
```

So you have a general class of:

# **Every-other-frame event resurrection**

This can affect:

* menu actions
* F
* R
* Delete
* M
* T
* F5–F11
* Enter
* mouse buttons
* debug-terminal activation
* mode toggles
* spawn actions

That means the UI isn't merely "occasionally responding twice."

**Its event lifetime semantics are fundamentally broken.**

```text
GTK tick callback
       ↓
simulation
       ↓
GTK label mutation
       ↓
queue GL redraw
```

The label is a normal GTK widget.

The simulation is updating the OpenGL object's state.

Then GTK eventually decides when to paint the whole hierarchy.

There is no explicit:

```text
simulation snapshot
        ↓
render snapshot
        ↓
GTK frame
```

boundary.

So UI and GL state are simply whatever happens to be current when GTK gets around to painting.

Usually that's okay.

Under load, resize, compositor pressure, or a slow physics step, it becomes visually inconsistent.

---

# ☠️ The robot visual proxy has an even more direct 60 Hz snapping problem

This is important.

`gui_robot_tick()` does:

```c
while (robot_accumulator >= fixed_robot_dt) {
    ...
    physics_world_step(...);
}
```

then immediately:

```c
dst->position = src->position;
dst->orientation = src->orientation;
```

So the render object is set to the most recent **completed 60 Hz physics state**.

There is no:

```text
previous_state
current_state
alpha
```

and therefore no interpolation.

Your renderer is perfectly capable of rendering at 144 Hz.

You're simply feeding it:

```text
60 Hz sampled positions
```

and asking it to display them at the monitor rate.

That's textbook temporal aliasing.

---

# ☠️ The legacy world has the same problem

`simulation_physics_tick()` also only advances its world in:

```c
1.0f / 60.0f
```

increments.

But `render_scene_current()` reads:

```c
rigid_body->position
rigid_body->orientation
```

directly.

Again:

```text
60 Hz state
     ↓
144 Hz render
```

with no interpolation.

So even if you completely removed MFS, the current high-refresh display path would still exhibit stepping.

---

# ☠️ There is no explicit render-state snapshot

The renderer directly reads mutable simulation objects:

```c
rigidbody *rigid_body = &obj_per_scene[object_index];
```

while the simulation has just modified those objects.

You're relying entirely on:

```text
"everything happens on the GTK main thread"
```

for consistency.

That works against actual data races, but it doesn't solve temporal consistency.

You need:

```text
simulation state
        ↓
render state
        ↓
renderer
```

even if the snapshot happens on the same thread.

---

# ☠️ Camera has a separate problem: movement is intentionally velocity-based

Your camera movement does:

```c
horizontal_velocity += direction *
                       movement_speed *
                       8.0f *
                       delta_time;
```

then:

```c
horizontal_velocity -=
    horizontal_velocity *
    friction *
    delta_time;
```

then the latest commit adds:

```c
if (!W && !A && !S && !D)
    horizontal_velocity = 0;
```

So the camera's behavior is:

```text
press W
    ↓
accelerate

release W
    ↓
instant stop
```

That is already a hybrid acceleration/teleport model.

But because your input state is alternating:

```text
W true
W false
W true
W false
```

the camera gets:

```text
accelerate
stop
accelerate
stop
```

which makes the display itself look like it is shaking.

So the apparent "text jitter" can actually be accompanied by **camera micro-motion**.

The entire OpenGL scene is then shifting underneath the GTK text overlay.

That makes the visual artifact substantially more noticeable.

---

# ☠️ IJKL is even more directly tied to frame cadence

This:

```c
float ijkl_speed =
    g_cfg.camera.ijkl_speed * frame_delta_time;
```

means rotation is frame-time based.

That's normally good.

But with:

```text
I true
I false
I true
I false
```

the camera rotates:

```text
Δθ
0
Δθ
0
```

rather than:

```text
Δθ
Δθ
Δθ
Δθ
```

So the camera motion itself is visibly discontinuous.

# ☠️ Focus handling can resurrect keys

Your focus-out handler clears:

```c
input_write->w_key_pressed = false;
...
input_write->i_key_pressed = false;
```

It does **not clear both buffers**.

So:

```text
focus lost
 ↓
write cleared
 ↓
read still says W=true
 ↓
swap
 ↓
W comes back
```

This is exactly how you can get:

> "I tabbed out / opened a dialog / clicked something and now the movement is stuck."

The focus system is not actually authoritative over input state.

---

# ☠️ Dialogs make the problem worse

You have:

```c
if (editor_dialog_is_active()) {
    return TRUE;
}
```

at the top of the physics callback.

So while a dialog is active:

```text
simulation stops
```

but GTK is still processing:

* keyboard events
* mouse events
* focus events

into the input buffers.

Therefore when the dialog closes, the simulation can resume with a backlog of stale input state.

That's another route to:

> phantom movement.

---

# ☠️ Opening the terminal changes focus domains

The terminal explicitly does:

```c
gtk_widget_grab_focus(terminal_entry);
```

while the main window's keyboard state is still being maintained separately.

When terminal focus changes:

```text
main window loses focus
terminal gains focus
```

your focus-out handler clears only the current write buffer.

Again:

```text
other buffer = potentially stale
```

so terminal interaction can leave the simulation input in a corrupted state.

---

# ☠️ Your event handlers are attached to the main window, not the actual interactive GL surface

You have:

```c
g_signal_connect(g_main_window,
                 "key-press-event", ...);

g_signal_connect(g_main_window,
                 "motion-notify-event", ...);
```

and:

```c
gtk_widget_add_events(g_main_window, ...)
```

This makes the **top-level window** the event surface.

That's workable for keyboard events.

It is substantially less clean for mouse-relative simulation because the actual mouse target is:

```text
GtkWindow
 └── GtkOverlay
      ├── GtkGLArea
      └── GtkLabels
```

The pointer can therefore interact with child widgets and propagation paths.

For a game-like surface, I'd make the GL area the actual pointer/keyboard input target and deliberately make overlay widgets non-interactive unless they need interaction.

---

# ☠️ You never explicitly make the GL area the focus target

Instead:

```c
gtk_widget_set_can_focus(g_main_window, TRUE);
gtk_widget_grab_focus(g_main_window);
```

The main window is being used as a pseudo-input device.

I'd much rather have:

```text
GtkWindow
   │
   └── GtkOverlay
         │
         └── GtkGLArea
               ↑
             focus
               ↑
          keyboard input
```

and then let actual GTK widgets take focus only when needed.

That makes focus ownership explicit.

---

# ☠️ Your Linux build forcibly switches to X11

You have:

```c
g_setenv("GDK_BACKEND", "x11", TRUE);
```

under Linux.

That means you're deliberately bypassing Wayland if the system otherwise supports it.

For a simulator whose mouse implementation already relies on:

```c
gdk_device_warp()
gdk_window_get_origin()
```

this is understandable.

But it also means your Linux display behavior is tied to:

```text
X11 + GTK3 + XInput/GDK pointer semantics
```

rather than modern compositor-neutral GTK behavior.

It isn't the primary regression, but it is a platform-specific source of future pain.

---

# ☠️ Your mouse coordinate system is also inconsistent

Windows:

```c
event->x
event->y
```

which are widget-relative.

Linux:

```c
event->x_root
event->y_root
```

which are root-window coordinates.

Then Linux manually calculates:

```c
screen_origin + widget_center
```

while Windows simply subtracts previous widget-relative positions.

So the two platforms aren't using the same coordinate model.

That means DPI scaling, window movement, multi-monitor transitions, and fractional scaling can produce different mouse behavior.

---

# ☠️ Linux center calculation doesn't account for scale factor

Your render path explicitly does:

```c
allocated_width * scale_factor
```

but the mouse path uses:

```c
gtk_widget_get_allocated_width(widget) / 2
```

without the scale factor.

So on a HiDPI display:

```text
render coordinate system:
    physical pixels

mouse center:
    logical GTK pixels
```

Those aren't necessarily the same coordinate space.

That can create a systematic mouse-centering offset.

On a 200% display, this can become enormous.

And that is especially nasty because you're then warping the cursor to the wrong location.

---

# ☠️ The 80-pixel mouse delta clamp is arbitrary and frame-rate dependent

You have:

```c
if (delta_x > 80) delta_x = 80;
if (delta_x < -80) delta_x = -80;
```

This is applied to an event delta.

If the pointer moves rapidly, GDK can deliver different event batching depending on load and platform.

So:

```text
slow:
    20 + 20 + 20

fast:
    80
```

can produce different total camera rotation.

This makes camera sensitivity dependent on event batching.

A relative-input accumulator should accumulate raw deltas and consume them once per frame, rather than arbitrarily truncating each individual event.

---

# ☠️ And you're overwriting mouse delta rather than accumulating it

This:

```c
input_state->mouse_delta_x = delta_x;
```

means if five motion events arrive before the next simulation tick:

```text
event 1: +5
event 2: +4
event 3: +7
event 4: +3
event 5: +8
```

you don't get:

```text
+27
```

You get:

```text
+8
```

the last event.

That's catastrophic for high-polling-rate mice.

It makes camera movement dependent on how GTK batches pointer events.

The correct operation is:

```c
mouse_delta_x += delta_x;
mouse_delta_y += delta_y;
```

followed by consumption/reset once per frame.

---

# ☠️ The overlay text update is not change-aware

You could avoid a massive amount of GTK churn by keeping:

```c
static char previous_text[...];
```

and only doing:

```c
gtk_label_set_text(...)
```

when:

```c
strcmp(new_text, previous_text) != 0
```

Right now, every frame effectively says:

> "GTK, here is some text."

even when nothing meaningful changed.

---

# ☠️ The renderer has no explicit GL error discipline

`render_init()` checks shader creation:

```c
if (...) {
    render_init_status = RENDER_FAILED;
}
```

but after initialization, the rendering path has essentially no:

```c
glGetError()
```

diagnostics.

For a cross-platform GL program, especially one running through GTK's GLArea, I'd want a debug-only GL validation layer.

Something like:

```text
before frame
after clear
after grid
after instancing
after utility rendering
after swap
```

with `glGetError()` assertions.

Not because I think GL errors are the current primary problem — I don't.

Because when you're trying to make the software **fear you**, you don't let the GPU silently participate in the conspiracy.

---

# ☠️ Resource cleanup is lying

`render_cleanup()` does:

```c
free(sphere_instances);
free(cube_instances);
render_init_status = RENDER_UNINITIALIZED;
```

but does not delete:

* shader programs
* VAOs
* VBOs
* meshes
* textures, if any

So the function is called:

```c
render_cleanup()
```

but it doesn't actually clean up the GL resource set.

For the normal one-process lifetime, this may not hurt much.

But if the GL context is recreated or the renderer is reinitialized, you've got a resource lifecycle problem.

---

# ☠️ There is no explicit swap/render policy

The program assumes GTK's `GtkGLArea` handles presentation.

That's normal.

But there's no explicit control or diagnostic of:

```text
frame clock
render time
physics time
buffer swap time
```

So when you say:

> "the display is jittery"

the current architecture doesn't give you enough instrumentation to answer:

```text
Was the simulation late?
Was GTK late?
Was rendering late?
Was the compositor late?
Was the widget allocation changed?
Did the GLArea redraw?
Did the frame callback miss a refresh?
```

You need those numbers.

```text
        │                   │
```

# The hierarchy of fixes

If I were allowed to tear this subsystem apart, I would do it in this order.

## 🔥 Phase 0 — kill the double buffer

Immediately.

Not patch it.

**Remove it.**

For this architecture, GTK events and the simulation callback are on the same main thread.

Use one persistent state:

```c
static input_state input;
```

Held keys:

```text
keypress → true
keyrelease → false
```

Mouse:

```text
motion → accumulate delta
```

One-shot events:

```text
keypress → set event
simulation → consume and clear event
```

No two copies of the entire state.

---

# 🔥 Phase 1 — split input into state and events

Something like:

```c
typedef struct {
    bool w, a, s, d;
    bool i, j, k, l;
    bool space, shift;

    bool mouse_locked;

    float mouse_dx;
    float mouse_dy;
} input_state;

typedef struct {
    bool escape;
    bool f;
    bool r;
    bool delete;
    bool menu_1;
    ...
} input_events;
```

Then the semantics become unambiguous.

---

# 🔥 Phase 2 — make mouse relative input actually relative

On every event:

```c
input.mouse_dx += dx;
input.mouse_dy += dy;
```

At frame start:

```c
float dx = input.mouse_dx;
float dy = input.mouse_dy;

input.mouse_dx = 0;
input.mouse_dy = 0;
```

That's it.

No 80-pixel event clamp.

No fake centering state.

No `mouse_centered` in the input state.

---

# 🔥 Phase 3 — one simulation clock

I would make the architecture:

```text
GTK frame clock
      │
      ├── calculate frame dt
      │
      ├── consume input
      │
      ├── advance fixed physics
      │
      ├── update camera
      │
      └── prepare render state
              │
              ▼
          GL render
```

Physics stays fixed at:

```text
1/60 s
```

but the renderer gets:

```text
previous physics state
current physics state
alpha
```

---

# 🔥 Phase 4 — interpolation

For every renderable body:

```c
render_position =
    previous_position * (1-alpha) +
    current_position * alpha;
```

For orientation:

```text
slerp(previous_orientation,
      current_orientation,
      alpha)
```

Then the display becomes:

```text
physics:
A -------- B -------- C

render:
A . . . . B . . . . C
```

instead of:

```text
A A A B B B C C C
```

This is the correct way to make a 60 Hz physics engine look smooth on a 144 Hz monitor.

---

# 🔥 Phase 5 — make the UI a render consumer, not a simulation participant

Instead of:

```c
physics_step_increment()
    ↓
overlay_update()
    ↓
gtk_label_set_text()
```

I'd use:

```text
simulation
    ↓
UI state snapshot
    ↓
frame/render callback
    ↓
UI update if changed
```

And update labels **only when their contents actually change.**

---

# 🔥 Phase 6 — fixed UI geometry

For the center menus:

```text
GtkOverlay
    └── fixed-size centered panel
          └── label
```

or use:

```c
gtk_widget_set_size_request(...)
```

with explicit alignment.

The text should change *inside a stable rectangle*.

It should never move merely because:

```text
"9.99"
```

became:

```text
"10.00"
```

---

# 🔥 Phase 7 — instrument the bastard

I would add a debug HUD showing:

```text

  dt:       6.94 ms
  FPS:      144.1
  render:   1.7 ms

PHYSICS
  dt:       16.67 ms

  accumulator: 8.2 ms

INPUT
  W:        0
  I:        1
  mouse:    +13,-4

GTK
  scale:    1
  allocation: 1920×1080
```

Then you'll know immediately whether:

```text
input
physics
render
GTK
```

is the culprit.
